# 页面改动落到源码

在网页上调好的预览只存在于当前页面，刷新后消失。这条链路把它们变成真实仓库里的代码改动：记录页面上的改动，按知识库找到这个页面的代码仓库，在前端和后端各自的沙箱里拉取真实代码、修改、构建并启动预览。

## 使用

1. 在 Athena 的浏览器里打开页面，用元素工作区自己调整，或让 Agent 调整。两者可以混用。
2. 在对话里说明要把改动落到源码，例如「把我刚才改的标题和按钮样式落到这个页面的源码里，前后端都启动起来给我核对，不要推送」。
3. 首次处理某个网站时，Athena 会弹出「登记页面与代码仓库的对应关系」确认卡，列出网站、前后端仓库地址、目录、分支和依据。确认后记住，同一网站以后不再询问。
4. 任务结束时给出沙箱预览地址。需要提交时再明确要求；每次推送测试分支前都会单独确认。

## 每一步做了什么

**记录改动。** 每轮任务开始时，Athena 把当前页面上仍然显示的预览改动交给 Agent：谁改的（用户或 Agent）、改的是哪个元素、文字和样式的取值。拖动调整中尚未松手的临时状态不计入。Agent 调用 `workbench_prd_save` 后，需求文档里会多出「页面改动记录」一节，逐条列出这些改动，精确取值保存在文档末尾的证据里。不需要先选中元素。

**定位仓库。** `workbench_repository_resolve` 按网站地址查找已确认的对应关系。没有记录时，它告诉 Agent 去知识库里查找这个系统的仓库资料，不允许猜测；Agent 带着仓库地址、前后端目录、分支和资料链接再次调用，由用户在确认卡上决定是否登记。拒绝后不保存任何内容。对应关系保存在本机用户数据目录的 `repositories/mappings.json`，仅当前用户可读。

页面上还有未记录的预览改动时，定位仓库会被拒绝并提示先记录，避免源码工作漏掉页面上的改动。

**沙箱里的真实代码。** 宿主用本机的 Git 凭据把仓库基线取到一份本地镜像，打成 Git bundle，通过只在本机回环地址监听、带一次性令牌的传输地址交给沙箱。沙箱拿不到 Git 凭据，也不挂载本机项目。前端和后端各用一个沙箱，分别修改、构建、启动服务，预览地址只在本机可访问。

**提交（可选）。** 用户要求提交时，沙箱把各自的提交打成 bundle 上传。宿主校验后才会请求推送：基线必须是提交的祖先，改动必须在对应组件目录之内，不接受符号链接、子模块和 `.git` 路径。通过后合并到一条新的 `athena/…` 测试分支，推送前弹出「推送测试分支」确认卡，推送后读取远端提交号核对。不会改动主分支。

## 边界

- 仓库地址只接受不带凭据的 `https://`、`ssh://` 和 `git@host:path` 形式；目录必须是仓库内的相对路径。
- 访问仓库使用本机已有的 Git 凭据，不弹出交互式登录；没有权限时直接报错。
- 页面来自当前工作目录里的项目时，Agent 直接修改工作目录的源码，不走仓库定位。
- 设置了 `ATHENA_REPOSITORY_MCP_URL` 时改用外部仓库服务，见 [客户材料导出链路](customer-export-workflow.md)。
- 预览里的选择器和样式来自页面，Agent 需要在源码里找到对应的组件和样式再修改；记录与构建结果以工具返回为准，不以模型的文字为准。

## 验证

- `tests/repository-service.test.ts`：对应关系的登记、拒绝与遗忘，地址和目录校验，bundle 传输地址的令牌与来源检查，提交校验、推送确认与远端核对。
- `tests/element-requirements.test.ts`、`tests/browser.test.ts`：页面改动记录的内容与归属（需要本机 Chrome 的用例通过 `ATHENA_TEST_CHROME` 启用）。
- 2026-11-15 在独立档案中用真实 Codex 跑通一次完整链路：用户手动修改标题和按钮样式，Agent 记录改动，从示例知识库读到仓库对照表并经确认登记，在两个沙箱里克隆同一基线，前端 `npm ci && npm run build`、后端 `mvn test package` 均以退出码 0 结束，两端服务通过健康检查，浏览器逐页核对 15 行按钮的实际样式与标题，全程未推送。总耗时约 14 分钟，其中约 5 分钟是新沙箱首次下载 Maven 依赖。真实模型的表现会随模型与页面而变，这一次结果不代表每次都能一次完成。
