# Athena 如何从网页操作演示中学习

2026-11-20 · 技术调研与原型建议 · 源码基线 `main@becec0a`

**建议把第一版定义为：用户演示一个流程，Athena 提出有证据的解释，请用户解决影响结果的歧义，然后在新对象上带用户完成并核验。** 学术上可以借鉴示教编程（Programming by Demonstration，PbD）、交互式程序归纳和基于最终状态的评测。研究支持这条路线的可行性；Athena 能学会多大范围的业务流程，仍须用自己的任务和模型测量。

## 一次演示能教会系统什么

假设用户给外部客户 A 导出材料，排除了内部备注。这段演示同时符合三种解释：所有导出都排除备注，仅对外导出时排除备注，或者用户只在这一次排除备注。软件即使记录了每个像素，也会看到同一段操作。三种解释的差别要到下一种情境才显现。

Lau 等把示教表述为从演示引起的应用状态变化学习可泛化的程序。形式上，给定演示 D 和允许的解释集合 H，可以保留其中所有与 D 一致的解释。新增一个能让这些解释作出不同预测的例子，才有机会排除其中一些。原论文在文本编辑器里实现了这个框架。WebRobot 后来直接在网页上验证了歧义的普遍性：76 个自动化基准里有 59 个产生多个符合演示的程序，其中 21 个产生不同的后续预测。其算法针对受限的网页操作语言；这些数字不能外推成业务规则的识别概率。[Lau 等，Machine Learning 2003](https://homes.cs.washington.edu/~weld/papers/mlj02.pdf) · [WebRobot，PLDI 2022，§5–7](https://web.eecs.umich.edu/~xwangsd/pubs/pldi22.pdf)

这带来一个产品选择。换成外部客户 B 可以检验系统是否把客户识别为可变参数，但 A、B 都是外部客户，两次成功仍然无法区分“所有导出”和“只对外导出”。最省力的澄清可以是一句“如果是给内部同事交接，这条排除规则还适用吗？”用户也可以回答“只管这次”或“我不确定”。由此得到的规则有适用范围和确认人。单个操作者的答复只在其有权定义的范围内生效。

## 四项设计决策的证据

1. **动作配上可观察的结果。** WONDERBREAD 的同模型对照中，GPT-4 根据任务描述和关键帧生成步骤说明，F1 为 0.71；加上点击和按键轨迹后为 0.82。另一组实验给出意图、关键帧和标准流程，判断整项任务完成的 F1 为 0.90，判断是否严格遵循指定步骤的 F1 为 0.27。这支持把多种证据结合，并分别评价结果和过程。实验没有单独比较 Athena 的结构化事件与视频，关键帧的增益要在本产品验证。[WONDERBREAD，NeurIPS 2024，表 3、5](https://arxiv.org/html/2406.13264v2)
2. **只问会改变下一步的问题。** Mayer 等在示例编程用户研究中，用能区分候选程序的具体例子主动提问，观察到错误减少，完成用时没有显著变化。PUMICE 则让用户结合手机界面演示和自然语言澄清含糊概念与条件，在 10 人实验中验证交互可行。对 Athena 的推论是模型先给出具体分歧，允许纠正、补演示或保留未知；不用每个点击都确认。这两项研究没有证明对企业规则的自动推断准确率。[Mayer 等，UIST 2015](https://www.microsoft.com/en-us/research/publication/user-interaction-models-disambiguation-programming-example/) · [PUMICE，UIST 2019](https://www.cs.cmu.edu/afs/cs/usr/mitchell/ftp/pubs/Li_Pumice_UIST19.pdf)
3. **把示例中的对象和要复用的步骤分开。** SUGILITE 利用界面层级、用户演示和自然语言识别参数及可能的值；WebRobot 利用动作和 DOM 轨迹生成后续操作的候选。由此可以尝试将“客户 A 这一行的导出按钮”表示为“当前指定客户所在行内的导出按钮”。角色、可见名称、行标题是重新定位的线索。旧页面的引用或坐标只适合回看演示。前者是移动端研究，后者的网页任务有明确边界；跨页面改版的可靠性要另测。[SUGILITE，ACL 2020 系统论文](https://aclanthology.org/2020.acl-demos.25/) · [WebRobot](https://web.eecs.umich.edu/~xwangsd/pubs/pldi22.pdf)
4. **业务结果由独立检查判定。** WebArena 使用功能正确性验证器，例如检查指定代码仓库中实际产生的内容。Athena 可以允许用户从搜索或列表到达同一客户，用同一组产物条件验收两条路径。如果某一步本身是业务要求，例如必须由本人批准，则另设过程条件，两项分别出结果。[WebArena，ICLR 2024，作者项目与评测说明](https://webarena.dev/og/)

## 当前代码和最小实现

当前录制保存带 ID 的事件，包括时间、URL、人或 Agent、元素、值及编辑归属。分析入口将整个录制对象交给通用只读会话，再把自由文本写入 `summary`。重复分析会把上次摘要再次送入上下文。网页运行时就绪时，通用会话还可能附上当时的标签页信息。原有模型验收核对输入框名称、输入值和按钮名称，未要求模型发现规则或换客户验证。[录制类型](../src/shared/types.ts) · [录制分析与会话调度](../src/main/main.ts) · [模型验收定义](../tests/live-agent.e2e.ts)

**第一步，把录制和解释分开。** 保留原始步骤与旧录制的读取方式。为分析构造只包含选定录制的脱敏输入，排除旧摘要、当前网页与无关工具。先按页面和目标整理事件，保留撤销、纠错、交接和失败。原录制合并相近的连续输入，普通录制达 2,000 步后不再追加；新采集应显式标记不完整，旧数据缺少结果时保留“未观察到”。[录制采集与合并](../src/main/browser.ts) · [现有录制数据边界](user-guide.md#数据与凭据)

**第二步，让模型生成可审阅的流程草稿。** 建议每个关键步骤输出动作、来源步骤 ID、可变对象、观察到的结果，以及仍待确认的条件。宿主校验引用存在且属于本段录制；有效 ID 只证明出处存在，语义是否相符仍应可回看、纠正。模型提出的规则、用户的确认原话、独立检查结果分别保存。重复分析不会升级旧推断。首版使用现有模型推理即可，无需训练专用模型。

一条草稿可以这样读：“第 7 步，用户点击客户 A 所在行的导出按钮。第 8 步，宿主观测到与本次操作关联的下载完成。可替换参数是客户。待确认条件是哪些材料允许对外导出。文件内容尚未核对。”这里的编号是示意。模型负责把事件归并成任务、人负责决定规则，程序负责在拿到文件后检查结果。即使页面出现“成功”提示，最后一项也只能记作页面反馈。

对“导出”只增采少量能区分结果的信号，如对应页面的校验提示，或有关联的下载开始、完成、取消。动作与结果按页面代次、帧、下载标识和顺序关联。已有宿主下载事件可复用，但仅用“操作之后最先完成的下载”会串到其他标签页。无法唯一关联时标为未知。优先采用脱敏的结构化事件；仅在语义信息不足且用户允许时尝试局部关键帧。旧录制无法事后补齐当时未采到的画面。文件核验尽量在本地执行，模型只接收判定和经过筛选的依据。[浏览器下载与录制实现](../src/main/browser.ts)

**第三步，换对象带做。** 在用户已确认的范围内，把步骤转成现有 Guide 的查看、点击、填写动作。在新页面用当前客户标识缩小到一行，再找控件；遇到同名目标、控件消失或页面换代，重新观察，请人指出或停止。目前带做定位可择优匹配多个元素，末步跳过也可能得到流程结束状态。新入口须同时检查匹配唯一性、是否跳过必要步骤及业务结果。首版由用户实际操作，在普通 DOM、同一已知系统中验证；跨站、iframe、Canvas 和自动代办另行评估。[带做协议](guide.md) · [页面目标匹配](../src/main/browser-page-guide.ts) · [步骤结束条件](../src/main/browser-guide.ts)

## 用客户导出来检验理解

现有 Meridian 演示有两名虚构客户 C1001 和 C1008；测试脚本能解包核验材料归属和内部备注标记。现有案例规定排除内部备注。上文的“取消勾选”和“内部交接”是研究设计的对照情境，若要真实演示这一步，应准备支持该选择的测试页面。[导出案例](customer-export-workflow.md) · [ZIP 验收脚本](../tests/customer-export-video.e2e.ts)

本次在本机对历史演示中的两份 ZIP 做了离线复核。检查固定四个条目、`customer.json` 的客户 ID、各文件的示例归属标识以及测试数据约定的 `INTERNAL_ONLY` 标记。A 和 B 各自通过；用 A 的文件冒充 B 时判为客户不符；给 B 的材料在内存中追加内部标记时判为违规；没有文件时返回未知。这证明该案例可构造独立判定，不能证明模型学会了流程。真实系统要按业务数据定义允许导出的字段和材料清单，单个测试标记只能覆盖示例。

**下一轮实验。** 同一批脱敏录制、同一模型及版本，比较现有摘要、带引用的流程草稿、流程草稿加一次针对性澄清三个条件。三个条件的输出都交给同一个带做执行入口处理，固定结果检查器、新案例和操作权限。这样能把差异归到演示的解释方式。另做是否增加局部关键帧的对照，决定收益是否抵得过时延、成本与隐私开销。

- **换数据。** 演示 A，只提供目标 B。检查能否找到 B，并拿到属于 B 的产物。测试用的新客户和正确文件独立保留，不进入演示上下文。
- **换规则适用条件。** 比较对外发送和内部交接。请业务负责人预先给出允许范围，记录系统是否提出有效问题、是否擅自把一次选择变成通用规则。
- **换页面与失败方式。** 调换两行顺序、放入两个同名按钮、让导出返回错误、在另一标签同时下载、或点击后无可核对结果。分别记录误指、误报成功和正确停下的次数。缺少证据时，允许流程报告未知。
- **分别计分。** 技术指标用关键步骤引用正确数／被抽查引用数、换对象后完整达标数／全部案例数、失败被报成成功的次数。体验指标用每次任务的澄清数、用户纠正数和达到可核验结果的耗时。报告样本量、具体失败和每项分母；两个客户只够路演演示。出现跨客户误指、包含内部数据仍报成功或必要步骤跳过仍报通过，均应挡住该场景的演示放行。

**周一的展示边界。** 先挑一个同站流程，展示一次有出处的解释、一处用户纠正、一次换客户带做，以及一个足以推翻错误结果的检查。做完以后可以准确地说“在这个流程和这些对照条件下验证过”。从任意录屏推断企业制度、跨系统自动执行及模型成功率，都需要另外的证据。
